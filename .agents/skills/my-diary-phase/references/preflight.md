# 作業前確認

## 使い方

個別プロンプトの基準状態と実リポジトリを照合してから変更する。コマンド名を固定的に仮定せず、`package.json`、Supabase設定、既存ドキュメント、直近の作業手順を確認し、このプロジェクトで実際に使われているコマンドを選ぶ。

## Git

最初に個別プロンプトの許可範囲から、通常Phaseか、ファイルシステムとGit管理領域への書き込みを禁止する厳密な読み取り専用Phaseかを判定する。

### 通常Phase

個別プロンプトがremote-tracking refなどGit管理領域の更新を許可する場合は、`git fetch origin`で比較対象を更新する。ネットワークまたは権限エラーを無視しない。

### 厳密な読み取り専用Phase

- `git fetch`を実行しない。
- 可能であれば`git ls-remote origin refs/heads/main`で実リモートmainを読み取る。
- 現在のローカルHEAD、ローカルの`origin/main`、`git ls-remote`で取得した実リモートmainを個別に報告する。
- ローカルの`origin/main`は更新していないため、実リモートmainと照合できるまでは古い可能性があると明記する。
- ネットワークまたは認証のため`git ls-remote`を実行できない場合は、「実リモート未確認」と報告し、fetchへ切り替えない。実リモートの確認が安全条件なら変更せず停止する。

### 共通確認

1. `git branch --show-current`でbranchを確認する。
2. `git rev-parse HEAD`と、個別プロンプトが指定する基準HEADを比較する。
3. `git rev-parse origin/main`でローカルの比較先を確認する。
4. `git rev-list --left-right --count HEAD...origin/main`で、ローカルの`origin/main`に対するahead/behindを確認する。
5. `git status --short`と必要に応じて未追跡ファイルを含むstatusでワークツリーを確認する。
6. 変更前に`git diff`と`git diff --cached`の有無を確認し、ユーザーの既存変更を今回の変更と混同しない。

HEAD、branch、同期状態、ワークツリーが個別プロンプトの基準と異なる場合、または予期しないSkill・Codex設定・差分がある場合は変更せず停止する。stash、reset、clean、checkout等で差分を退避・破棄しない。

## 秘密情報と環境ファイル

- `.env.local`の値を表示・報告しない。存在確認やGit追跡状態の確認だけで足りる場合は内容を読まない。
- `.env.local`や秘密情報をstageしない。`.env.example`には変数名だけを置くという`AGENTS.md`の規則を守る。
- 認証情報が必要な検査を、値の読み取りや出力で回避しない。既存の安全な認証経路で実行できなければ未実施として報告する。

## migrationとDB

- `supabase/migrations`の履歴、Git差分、命名順を確認する。
- ローカル・linked環境のmigration状態確認は、個別プロンプトが許可し、既存のプロジェクト手順と認証で安全に実行できる場合だけ行う。
- migration作成や適用を状態確認と混同しない。読み取り専用確認から`supabase db push`、repair、resetへ進まない。
- 既存migrationを編集しない。DB変更なしのPhaseではmigrationを作成・適用しない。

## Docker DesktopとローカルSupabase

- DB検証に必要な場合だけ、最初にDocker CLIの存在を確認し、次にDocker daemonへ接続可能か確認する。勝手に起動・再起動・停止しない。
- Docker daemonが利用不能なら、ローカルSupabaseも利用不能または未確認として理由を報告する。Supabase CLIを追加で呼び出さず、権限昇格、設定変更、リモート環境での代替を行わない。
- Docker daemonが利用可能な場合だけ、個別プロンプトの許可範囲と既存のプロジェクト手順に従って、ローカルSupabaseの状態を確認する。
- 厳密な読み取り専用Phaseでは、ユーザー領域などへの書き込みが判明しているCLI操作を行わない。実行中に書き込み要求を検出した場合はその時点で停止し、実行できなかった確認項目と理由を報告する。設定変更や権限昇格で回避せず、正式に確認していないtelemetry無効化用の設定名や環境変数を推測で使用しない。
- 通常の実装Phaseでは、CLI利用を一律に禁止せず、個別プロンプトの許可範囲に従う。
- ローカル環境であることを確認せず`supabase db reset`を実行しない。通常Phaseでは個別プロンプトの明示許可なしにresetしない。

## 開発サーバーと既存プロセス

- UI検証が必要な場合だけ開発サーバーの既存プロセスとポートを確認する。
- 安全に再利用できる既存サーバーは再利用する。所有者や用途が不明なプロセスを終了しない。
- ポート競合、古いbuild、環境不一致を確認する。強制終了は個別プロンプトの明示許可がある場合だけ行う。
- 強制終了が必要だが許可がない場合は、変更せず停止するか、別ポート等の非破壊的な手段がPhase範囲内ならそれを使う。

## 実装前の基準検証

変更の種類とリスクに応じ、既存pgTAP、lint、typecheck、build、対象画面、認証・RLS・visibility、migration履歴から必要な項目を選ぶ。個別プロンプトで不要とされた重い検証を無条件に実行しない。既存失敗を発見した場合は結果を保存し、今回の変更に含めて勝手に修正しない。

## 停止条件

- 必須入力が不足し、安全な作業範囲を確定できない。
- Git状態または基準HEADが個別プロンプトと異なる。
- 未コミット変更、予期しないSkill・Codex設定、またはユーザー変更がある。
- `AGENTS.md`、Skill、個別プロンプトが矛盾する。
- 必要なDB・認証・環境の状態を安全に確認できない。
- 厳密な読み取り専用Phaseで、必要な確認にファイルシステムまたはGit管理領域への書き込みが必要になる。
- 読み取り専用のCLI操作で書き込み要求を検出する。
- 許可されていないmigration、package、リモートDB、破壊的操作が必要になる。
- 既存プロセスの強制終了が必要だが明示許可がない。
